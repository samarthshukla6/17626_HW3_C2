# Learning log

Team: Samarth Shukla and Kevin Huang. 17-626 Requirements for Information Systems, Assignment 3.

This log records the decisions we made during the sprint, what we saw when we used the prototypes, and what we learned. The supporting detail is in `docs/goal-model.md` (scope, conflicts, assumptions and the V2 revisions), `docs/traceability.md` (the matrix and every finding) and `specs/001-schedule-change-record/` (the Spec Kit artifacts). We used an AI coding agent through GitHub Spec Kit to generate the specs, plans, tasks and code. The decisions and judgments described here are ours.

## 1. Sprint planning and requirements selection

We interviewed the same three stakeholders separately, so we started with two sets of transcripts and two A2 goal models. Samarth's model was larger: about 130 goals, 13 use cases and 8 recorded conflicts. Kevin's had 71 goals and 9 use cases, but it held evidence Samarth's lacked. Ruth asked Kevin for failed deliveries to be visible and for unverified items to be labelled. Melissa described pickups to Kevin as "completed, refused, or missed". Ruth also told Kevin that a dismissed tone warning should stay visible in the record. Both models numbered goals from G-1, so we kept every original ID and added an `S-` or `K-` prefix. That way anything we trace can still be found in the A2 submission it came from.

We sorted the merged goals into ten candidate slices and scored them on the handout's three criteria. We added a fourth question: does anything else depend on this slice? We chose one feature made of three slices: agreeing a schedule change, honest timing of requests and responses, and an append-only record with an author on every entry.

It is core because every stakeholder named the custody schedule first when we asked what the app must get right (E-01, E-02, E-03), and nearly every later slice needs the record. It is user-facing because both parents use it every week, and Melissa's biggest worry was that Jason would refuse a complicated app (E-56). It carries the most uncertainty because it contains the two conflicts we were least sure how to settle: the 48-hour notice rule against Jason's route changes, and the time on a phone against the time on a server.

Expenses were the hardest slice to leave out. They are just as core and visible, but the interviews already settle the rules (medical and school costs split 50/50, child support kept separate), so a prototype would mostly confirm what we already knew. Export and reviewer access need content from other slices first. School notices depend on outside systems. Tone warnings have an unresolved conflict. The child's view is lower priority, and calls stay outside the app until someone checks the court order. All of these remain in the goal model as deferred slices D to J.

The goal model showed us how the selected requirements relate. Five pairs of goals from the two models were the same need in different words, and we combined them. The message timestamps are one example: Jason gave us "when I wrote it", Ruth gave us "failed delivery should be visible", and neither model had every state. Two pairs looked similar but had to stay apart. "Overdue" is a flag on a pending request, not a new status, because Melissa did not want an unanswered request to look like a decision. Every action writes to the record, so the event log and the trusted clock had to be built first.

For conflicts, we never removed a goal. Both of us had found the 48-hour conflict on our own, which made us confident it was real. We chose a compromise: a short-notice request goes through, gets labelled, and still needs written agreement from both parents. That matches Melissa's own condition that she would consider a late change "only if it truly works for the kids" (E-17). Reading that conflict next to the clock conflict exposed a third question that neither A2 model asked (X-3): if Jason writes a request at a truck stop 50 hours before pickup and it reaches the server 46 hours before, how much notice did he give? For V1 we chose the server time and showed the written time next to it, and we made this the main thing V1 would test. Kevin's interview with Ruth also contradicted one of Samarth's tacit goals (S-G-152, a tone warning kept private to the sender). We marked it contradicted instead of deleting it, because its clash with Jason's fear of being judged is still open.

## 2. Prototype evaluation

Kevin used the deployed V1 as both parents and worked through twelve scenarios, from creating a request to failed deliveries and reloading the page. The findings are in `docs/traceability.md`. The most significant are below.

The truck-stop case (F-6) taught us the most. Jason wrote a request offline 50 hours before the exchange and it reached the server 46 hours before. V1 labelled it "Short notice: 46 h given". That was exactly what our spec said should happen, so this was a requirements issue, not a code defect. The rule we wrote to satisfy Ruth's demand for trusted time (E-32) would have made Jason look careless in the one situation he described to us as unfair (E-36, E-62). Reading the two goals on paper, we saw a reasonable compromise. Seeing the label on a card made it obvious which parent the compromise hurt.

The read receipt (F-3) was the second clear requirements issue. Melissa's card switched to "Read" the moment she opened Home, even though she had not looked at the request. Our assumption A-7 said "read" meant "opened in the app", which was too vague to separate glancing at a list from reading a request. Jason's whole concern was a record that makes him look as if he ignored something (E-30), and a receipt that fires on its own would create exactly that kind of false evidence in the other direction.

Delivery states produced two more requirements issues. While Melissa was offline, a request showed "Not delivered yet", which reads almost the same as a real failure (F-4). The spec simply had no state for "waiting". And a failed delivery could never be retried (F-5), because the spec never said what should happen after a failure. A queued request also showed "Status: Pending" before the server had it (F-2), because the spec only defined status for requests the server holds.

Only one finding was an implementation defect in the strict sense: the offline card did not show its written time, which FR-010 clearly asked for (F-1). Kevin also recorded four usability problems (F-7 to F-10). Later code inspection showed that one of them, the alternative time on a decline that could not be completed (F-10), was actually a defect, because the code replaced the input's value with one the control could not display.

The way we told the two types apart was to ask one question each time: if the agent had followed the spec perfectly, would the problem still be there? For F-2 to F-6 the answer was yes, so the spec had to change. For F-1 and F-10 it was no, so the code had to change.

## 3. Revisions and learning

We changed the goal model and `spec.md` before touching any code, then regenerated the plan and tasks with Spec Kit and implemented them. Every change is listed in the spec's revision history and in `docs/goal-model.md` section 8.

The notice label (X-3, F-6). We first intended notice to be measured only from the server time, with the written time shown as a separate field. Evaluation showed that this hides Jason's situation while technically being fair. We changed the X-3 decision from "server time only" to a compromise: the server figure stays official and still decides whether the request counts as short notice, and when the written figure differs it appears next to it as unverified context. The truck-stop request now reads "Short notice: 46 h at server" with "Written 50 h before (device time, not verified)". Ruth's rule still decides, and Jason's effort is still visible. We kept Q-3 open, because only the stakeholders can say which figure should count.

The read receipt (F-3). We first intended "read" to mean the recipient opened the request in the app. Evaluation showed that rendering a card counted as reading it. We replaced A-7 with A-12: "read" means the recipient explicitly opens the request details. V2 records a read only after "Open details", so a read receipt is now evidence of an action the parent took.

Delivery states and retry (F-4, F-5). We first intended three outcomes: delivered, read and not delivered. Evaluation showed a fourth situation the spec had missed, and no way out of a failure. We added A-13 ("Waiting to be delivered (other parent offline)") and A-15 (the sender may retry, and a successful retry adds a delivery entry while keeping the failure in the history). V2 makes the difference between "not yet" and "failed" clear without removing anything from the record.

The unsent state (F-1, F-2). We first intended an unsent request to look like a pending one with a "saved on this device" label. We added A-14: an item that exists only on the sender's phone shows "Not sent yet" and its written time, with no status. This keeps statuses as statements about what the server holds.

Verifying V2 in the browser taught us one more lesson. The V2 tests passed, yet using the app found four more defects (F-11 to F-14). A request sent while Melissa was offline never became "Delivered" when she came back. The delivered time disappeared once something was read. Jason's "Request submitted" confirmation stayed on screen when we switched to Melissa. History still showed raw labels such as "Jason: create". Two of these had been in V1 all along, and neither our V1 review nor our Step 4 evaluation caught them, because our scenarios never took the receiving parent offline and back online, and never compared a card before and after a read. All four were defects against a spec that was already right, so we fixed them in code with a test for each, and recorded them as tasks T083 to T086 so the trace stays complete.

## Reflection

Several decisions needed our judgment rather than the AI's. We chose the scope by dependency as well as by the three criteria, and we kept both ID schemes when renumbering would have been easier. We noticed X-3, which only appears when two separate conflicts are read side by side. We downgraded one of our own tacit goals because a teammate's evidence contradicted it. When Spec Kit asked clarifying questions, we answered from interview evidence and recorded the answers as assumptions that say plainly no stakeholder raised them. When the agent dropped part of an answer (locking the emergency tag once sent), we put it back. We also refused to let the agent resolve Q-1 to Q-4 itself, because those need the stakeholders.

Prototyping changed our understanding of the stakeholders' needs. On paper, "server time is the trusted time" looked like a neutral technical rule. On a screen, it made one parent look worse in exactly the case he had described. In the same way, "read" sounded simple until we saw a receipt appear for something nobody had read. Both stakeholders care less about any single timestamp than about the record never saying something that did not happen. That only became clear once we could see the record.

Spec-driven development kept the requirements and the code consistent because one set of IDs ran through everything: REQ-nn in our spec, FR-0nn in Spec Kit's spec, task tags in `tasks.md`, test names and comments in the code, and rows in the matrix. The rule of changing the spec first meant every V2 behaviour change has a written reason before it has code. It did not catch everything. Spec Kit's own checklist and analysis steps found real problems in our wording and task order, but a full set of passing tests still left the app unusable in V1 (no way to create a request, a five-hour time shift, a wrong mock schedule) and left four defects in V2. Requirements traceability told us what to build. Only using the app told us whether it had been built.

If we had to show management the value we added beyond what the AI generated, we would point to concrete artefacts. The checklist review found 25 wording problems that we fixed in the spec before any code was written, including an open-ended banned-word list that made one success criterion untestable. Our review of the plan added five missing pieces, among them a definition of when "delivered" happens. Browser testing found 11 defects in V1 and 4 in V2 that the agent had reported as done with all tests passing. Most of all, F-6 shows a requirements decision that was internally consistent and still wrong for one stakeholder. No amount of generated code would have revealed that without someone deciding to test the truck-stop case and then judging what the result meant for Jason and Ruth.
